# ID 方案

> 本文档定义 ID 的形状与取值来源。机器可读的前缀表在 `../schema/taxonomy.yaml`。

## 形状

```
<前缀>_<26 位 Crockford base32>
```

- **前缀进 ID，不只进字段。** 于是 `grep`、按前缀分区目录、日志里一眼看出类型
  都成立。类型信息放在两处比放在一处更难丢。
- **26 字符**固定长度：130 位（实际使用 128 位，末尾补 2 个零位）。
  固定长度让正则与分区逻辑简单。
- **Crockford base32**：`0123456789ABCDEFGHJKMNPQRSTVWXYZ`。
  不含 `I`、`L`、`O`、`U`：前三个与 `1`、`0` 手抄时容易混，`U` 整个排除是为了
  拼不出脏词。解析时先归一化再比较：`I`/`L` → `1`，`O` → `0`，大小写不敏感。
  不做这一步，`supersedes` 这类引用会因为手抄差异**静默断链**。

## 前缀表

| 前缀 | 含义 | 分区目录 | 备注 |
|---|---|---|---|
| `dec_` | decision（决策） | `assets/dec/` | `accepted` 之后不可变 |
| `state_` | state（状态） | `assets/state/` | 就地替换，必须带日期 |
| `event_` | event（事件） | `assets/event/` | 只追加 |
| `rule_` | rule（规则） | `assets/rule/` | 就地替换，必须绑 `origin_incident` |
| `src_` | 来源（**不是资产类型**） | `sources/src_.../` | 只读层 |

前缀表本身在 `../schema/taxonomy.yaml` 的 `asset_types.*.prefix`，不写在代码的注释里：
类型和它的前缀必须一起改，两处维护必然漂移。

## 取值来源：能重算的用内容寻址，不能重算的用 ULID

判据只有一条：**这个东西能不能重算出来。**

| | 能不能重算 | 取值 | 为什么 |
|---|---|---|---|
| `src_`（来源） | 不能（原始字节） | `SHA-256(原始字节)` 前 128 位 | 同一份导出重复导入必须命中同一个来源，否则事件会翻倍 |
| `event_`（事件） | 能（sources + 连接器） | `SHA-256(source_id + key + text)` | 两次运行必须得到同一个 ID |
| `dec_` / `state_` / `rule_` | 不能（含人的判断） | ULID（48 位毫秒 + 80 位随机） | 它们需要一个"何时被写下"的语义 |

**派生 ID 里没有时间。** 时间戳进输出会让输出每次都不一样，快照测试只能关掉，
"确定性"就没有执行体了。事件的时序由 `occurred_at`（来自导出本身）承担，
而"编译发生在几点"对消费者没有价值。

## 已知代价

- 派生 ID 按字典序排序不再等于按时间排序。补偿：事件的排序键显式写成
  `(occurred_at 降序, ID)`。
- 内容变一个字，内容寻址的 ID 就变。对不可变数据这是正确行为，但它意味着
  "编辑一条事件"等于"新建一条 + 旧的成为孤儿"——这是有意的摩擦。
- ID 长（前缀 + 26 位），人读不如短编号顺眼。这是为"可离线生成 + 可排序"付的价。
