# 0005 · 格式版本与发布版本分两层

## 问题

规范需要一个版本号，但"能不能被读懂"和"这次发布了什么"是两个不同的问题。
只用一个 `1.0.0` 会让实现者以为 `schema_version` 也要写 `1.0.0`；只用一个整数
又无法标记发布批次。两件事必须同时表达，但不能混成一个字段。

## 考虑过的选项

1. **只保留格式版本（整数）**：简单，但发布批次只能靠 git tag 表达，
   文件和标签之间没有可校验的关系。
2. **只保留发布版本（`x.y.z`）**：语义清晰，但每条资产的 `schema_version`
   会变成三段，而实现只关心主版本。
3. **两层并显式映射**：格式版本是整数，发布版本是 `x.y.z`，主版本必须相等。

## 选定

两层并存：

- **格式版本**：`schema/taxonomy.yaml` 的 `version`（当前 `1`），也写在每条资产的
  `schema_version` 里。它决定文件能不能被读懂。
- **发布版本**：`VERSION` 的 `x.y.z`（当前 `1.0.0`），对应标签 `spec-vX.Y.Z`。
  它只标记发布批次。
- **映射**：发布版本的主版本号必须等于格式版本（`1.0.0` ↔ 格式 v1）。
  `validate.mjs` 会校验，不一致时分别报 `VERSION_MISMATCH` 或 `VERSION_INVALID`。

不兼容变更升格式版本并提供迁移说明，发布版本随之升主版本；兼容的澄清与示例
增补只更新文档与发布版本的次/修订号。

## 后果

- **好**：实现者只需要看整数；发布流程有一个可机器校验的标签对应关系。
- **代价**：多了一个 `VERSION` 文件，以及一条"两层必须对齐"的检查。
- **残余风险**：`VERSION` 不能替代迁移说明；它只证明发布批次，不证明兼容性。
