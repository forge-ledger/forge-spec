# 0002 · ID 前缀 + 26 位 base32；能重算的用内容寻址

## 问题

ID 应该在什么时候生成、由谁生成？如果 ID 带时间，输出就不确定；如果 ID 不带时间，
又怎么保证同一份输入重复处理时得到同一个结果？

## 考虑过的选项

1. **自增整数**：需要中心分配器；离线不可用。
2. **纯随机 UUID**：重复导入会产生新 ID，事件与来源会翻倍。
3. **前缀 + 内容/随机混合**：能重算的用内容寻址，不能重算的用 ULID。
4. **纯时间戳**：输出不确定，快照与审计失去执行体。

## 选定

- 形状：`<类型前缀>_<26 位 Crockford base32>`。
- 能重算的对象（来源、事件）用内容寻址：同一份输入必须得到同一个 ID。
- 含人的判断的对象（决策、状态、规则）用 ULID：它们需要"何时被写下"的语义。
- **派生 ID 里没有时间**；时间由业务字段承担。

## 后果

- **好**：离线可生成；重复导入幂等；grep 与目录分区都简单。
- **代价**：内容变一个字，ID 就变；"编辑一条事件"等于"新建一条 + 旧的成为孤儿"。
- **残余风险**：ID 较长，人读不如短编号顺眼。
