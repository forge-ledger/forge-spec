# 治理

## 目标

让规范的变化**可预期、可审查、可迁移**。标准的价值来自稳定；稳定的前提是
变更流程本身是公开的。

## 角色

- **维护者**：合并变更、发布版本、处理安全报告。当前由仓库 owner 担任。
- **贡献者**：提交规范文本、示例、校验规则或兼容性反馈。
- **实现者**：在本规范之外实现读取、写入或迁移工具的人。

## 变更类别

| 类别 | 例子 | 要求 |
|---|---|---|
| 澄清 | 改错字、补例子、解释已有规则 | 普通 PR；至少一位维护者批准 |
| 兼容增补 | 新增可选字段、新增示例 | RFC；说明旧实现如何忽略它 |
| 不兼容变更 | 删字段、改语义、改 ID 形状 | RFC + 主版本升级 + 迁移说明 |

## RFC 流程

1. 在 issue 里写清：要解决的具体问题、考虑过的选项、选定与后果。
2. 给出至少一个**合成**示例，说明变更前后的差异。
3. 维护者给出决定；决定记录进 `decisions/`。
4. 变更合并前，`node validate.mjs` 必须绿。

## 版本

- **格式版本**是 `../schema/taxonomy.yaml` 里的一个整数。
- 每条资产的 `schema_version` 必须等于它。
- **发布版本**是 `VERSION` 里的 `x.y.z`；它的主版本号必须等于格式版本。
- 不兼容变更必须升格式主版本，并在 `CHANGELOG.md` 里写迁移说明。

## 决策记录

公开的规范决策放在 `decisions/`。每条记录回答四件事：

1. 当时的张力是什么；
2. 考虑过哪些选项；
3. 选定了什么，判据是什么；
4. 代价与残余风险是什么。

## 不承诺日期

本仓库不承诺路线图日期。规范是长期格式，不是按季度交付的产品；
写进 README 的日期会变成负债。
